# 07. План разработки

Документ описывает этапы реализации HealthTracker, состав каждой версии, оценку трудозатрат и порядок работ. Оценка — в человеко-днях (ч/д) работы одного разработчика с фокусом.

## 1. Философия этапов

- **v0.1 — Локальный MVP** (3–4 недели). Работает на машине разработчика, база и файлы локально, без Docker. Цель — доказать, что продукт полезен и используется.
- **v1.0 — Self-hosted Release** (1–2 недели сверху). Готов к публичной установке через Docker Compose, автоматический HTTPS, бэкапы.
- **v1.1 — Quality of life** (1–2 недели). То, что выяснится «по горячим следам» — мелкие улучшения UX, исправления, доп. экспорт.
- **v2.0 — OCR + Симптомы** (3–4 недели). Ввод из PDF/фото через LLM-vision, журнал симптомов, теги.
- **v3.0 — Шеринг + Native** (неопределённо). Read-only ссылки для врачей, возможно Capacitor-обёртка для iOS/Android, импорт из ЛК лабораторий.

## 4. v1.1 — Quality of life (≈ 5–7 ч/д)

Приоритизируется после первого месяца реального использования. Ориентировочный состав:

- **Клавиатурные хоткеи**: `/` — поиск, `n` — новый замер, `Esc` — закрыть drawer.
- **Дубликат замера**: «скопировать прошлый замер как шаблон».
- **Улучшенный поиск замеров**: по тексту в заметке, по имени показателя, по диапазону значений.
- **Темы**: явный toggle, не только system.
- **Offline-режим**: улучшенная service worker стратегия, хранение изменений в IndexedDB при отсутствии связи.
- **Push-уведомления** (PWA): напоминание о пересдаче по интервалу.
- **Переопределение дефолтных референсов глобально на инсталляции**: admin может подгрузить свой CSV.
- **Улучшения графика**: увеличение (pinch-to-zoom), выделение диапазона для фильтра списка.

## 5. v2.0 — OCR и расширенные сущности (≈ 15–20 ч/д)

Главное расширение после MVP. Добавляет то, что было вынесено из scope MVP.

### 5.1. OCR/парсинг бланков (≈ 8 ч/д)

- Интеграция с LLM-vision API (Anthropic Claude или OpenAI GPT-4 Vision) с хранением API-ключа в env.
- Альтернатива: локальный Tesseract для текстового распознавания + LLM для структурирования.
- Pipeline: upload → OCR → извлечение `[{ metricName, value, unit, reference }]` → матчинг с справочником → форма предпросмотра для подтверждения пользователем → сохранение.
- UX подтверждения: пользователь видит извлечённые поля и правит до сохранения.
- Особое внимание — приватности: LLM-запросы идут только по явному согласию пользователя; опционально — offline-режим с Tesseract.

### 5.2. Журнал симптомов (≈ 3 ч/д)

- Модель `SymptomEntry { id, userId, takenAt, type, severity 1-10, note }`.
- Отдельный раздел интерфейса.
- Наложение на графики (вертикальные метки на дате симптома).

### 5.3. Лекарства и курсы (≈ 3 ч/д)

- Модель `MedicationCourse { id, userId, name, dosage, startedAt, endedAt, note }`.
- Раздел «Мои курсы».
- На графике — горизонтальные полосы сверху, отмечающие активные курсы.

### 5.4. Теги событий (≈ 2 ч/д)

- Модель `Tag { id, userId, name, color }` + `TagOnMeasurement`.
- Привязка к замерам.
- Фильтр в списке замеров.
- Вертикальные линии на графике для тегов типа «болезнь», «отпуск».

### 5.5. Несколько профилей / подопечных (≈ 4 ч/д)

- Модель `Patient { id, ownerUserId, name, sex, birthDate }`.
- Переход `Measurement.userId` → `patientId`.
- Переключатель профиля в UI (Анна → ребёнок Ваня → мама).
- Миграция существующих данных: для каждого User создаётся Patient из Profile.

## 6. v3.0 — Шеринг и Native (не приоритизировано)

Идеи для дальнейшего развития, приоритизация — по мере появления потребности:

### 6.1. Шеринг для врача

- Модель `SharedLink { id, userId, token, expiresAt, scopeJson }`.
- Генерация read-only ссылки с ограниченным сроком и набором показателей/замеров.
- Врач заходит по ссылке без учётки, видит публичную read-only версию данных.

### 6.2. Capacitor-обёртка

- iOS и Android приложение на той же кодовой базе React (Capacitor).
- Deeplinks, пуш-уведомления, доступ к камере из нативного контекста.

### 6.3. Импорт из ЛК лабораторий

- Для каждой лаборатории — свой парсер (HTML-скрейпинг или API, если есть).
- Юридическая проработка: ToS лабораторий, приватность.
- Начать с одной-двух (Helix, Инвитро).

### 6.4. Двухфакторная аутентификация

- TOTP через `otplib`, QR-код для Google Authenticator / Authy.
- Backup-коды.

### 6.5. AI-ассистент (осторожно)

- Объяснение значений на простом языке.
- Подсказки о паттернах в динамике.
- **Важно**: всегда с дисклеймером «не заменяет врача»; не даёт рекомендаций по лечению.

## 8. Принципы работы

- **Один PR = одна задача из таблицы спринтов**. Короткие PR, быстрые ревью.
- **Тесты пишутся одновременно с кодом**. Сервисы — юнит-тесты, эндпоинты — интеграционные.
- **Миграции — отдельными коммитами** с описательными именами.
- **Breaking changes — через deprecation**. Старый API живёт рядом с новым один релиз.
- **Секьюрити-апдейты — первоочередные**. `npm audit` в CI; при HIGH/CRITICAL — bloker для релиза.
- **Документация обновляется в том же PR**, что и код, если меняется API или модель.

## 9. Зависимости между задачами

Критический путь разработки v0.1:

```
1.1 → 1.3 → 3.1 → 4.1 → 6.1 → 6.7 (график показывается)
  ↓      ↓      ↓      ↓
 1.4 → 2.1 → 2.5 (авторизация работает)
           ↓
          4.2 (замеры создаются)
           ↓
          7.2 (экспорт)
```

Можно параллелить:
- Спринт 3 (справочник) и спринт 2 (auth) — независимы после 1.3.
- Спринт 4 (замеры) и спринт 5 (вложения) — первые задачи 5.1 и 5.2 можно начать сразу после 4.1.
- Спринт 6 (графики) требует готового 4.2 (endpoint `GET /measurements`).

Если работают двое разработчиков:
- Dev-1: авторизация → замеры → графики.
- Dev-2: справочник → вложения → экспорт.

## 10. Риски и буфер

Оценки даны для «нормального» темпа. Реальный темп обычно в 1.3–1.5 раза медленнее из-за:

- Непредвиденных багов (особенно в чарт-библиотеке и в CSRF-cookies).
- Правок UI после первых попыток использовать самому.
- Вариативности макета (новые требования по ходу).

**Рекомендованный буфер**: +30% к каждой оценке для консервативного плана.

Таким образом, v0.1 реалистично выходит за 5–6 недель работы одного разработчика с фокусом.
