# 10. Детализация вех (описание без коммитов)

Документ раскрывает каждую веху из `07_ROADMAP.md` и `09_COMMIT_PLAN.md`: цель, объём, результат, зависимости, риски и критерии готовности (Definition of Done). Коммиты будут расписаны отдельно после согласования содержания вех.

Единица оценки — **рабочий день разработчика** (≈ 5–6 продуктивных часов).

## Milestone 0 — Project Setup

**Цель.** Подготовить техническую базу так, чтобы любой новый функциональный коммит попадал в ту же единую инфраструктуру: общий линтер, форматирование, типы, CI, Docker-сборка. Это фундамент, переделка которого после старта продуктовой работы стоит в разы дороже.

**Объём.**
* Монорепо на pnpm workspaces: `apps/web`, `apps/api`, `packages/shared`.
* Единые TypeScript-настройки, путевые алиасы.
* Prettier + ESLint с общими правилами, husky + lint-staged для pre-commit проверок.
* Commitlint с enforcement Conventional Commits.
* GitHub Actions: lint + typecheck + (пока пустой) test-ранер.
* Скаффолды приложений: Vite+React+TS для web, Fastify+TS для api, Prisma init под SQLite.
* Tailwind + базовые компоненты shadcn/ui.
* React Router v6 с пустыми маршрутами-заглушками.
* Dockerfile для каждого приложения, `docker-compose.dev.yml` для локального запуска.
* `.env.example` с полным набором переменных.

**Результат.** `pnpm install && pnpm dev` поднимает пустой web (с роутами login/register/home) и api (с `/health`), обращающиеся друг к другу через прокси Vite. CI проходит зелёным на пустом коде.

**Зависимости.** Нет.

**Риски.**
* *Разнобой версий Node/pnpm между участниками* → фиксируем в `.nvmrc` и `packageManager` в `package.json`.
* *Длинный setup съедает темп* → ограничиваем milestone одним днём; не полируем то, что понадобится позже (никаких шаблонов страниц сверх заглушек).

**Definition of Done.**
* `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test` (заглушка) проходят локально и в CI.
* Conventional Commit нарушающий сообщение отклоняется husky-хуком.
* `docker compose up` поднимает оба сервиса, `curl http://localhost:3000/health` отвечает 200.

**Оценка:** 1 день.

## Milestone 1 — Auth

**Цель.** Закрытый периметр: все данные медицинских измерений персональны, без аутентификации приложение нельзя показывать даже в dev-демо.

**Объём.**
* Модели `User` и `Session` в Prisma, первая миграция.
* Регистрация, вход, выход, `GET /auth/me`.
* Хранение сессий в БД (серверный state), cookie `sid` — `HttpOnly; Secure; SameSite=Strict; Path=/`.
* bcrypt для паролей (work factor 12).
* CSRF: double-submit cookie, заголовок `X-CSRF-Token` на всех мутациях.
* Rate-limit на `/auth/login` (5 попыток / 15 мин на IP+email).
* Web: страницы login/register с валидацией Zod, обёртка `RequireAuth` для роутов, глобальный 401-handler с редиректом.
* Минимальные тесты критических путей (happy + auth failure + CSRF reject).

**Результат.** Пользователь может создать аккаунт, войти, обновить страницу (сессия жива), выйти. Защищённые API-роуты отказывают без сессии. CSRF работает.

**Зависимости.** Milestone 0.

**Риски.**
* *Неправильные cookie-флаги* — можно забыть `Secure` в проде или выставить `SameSite=Lax` и сломать CSRF-защиту. Покрываем e2e-тестом в CI и ревью prod-конфига.
* *Утечка email при брутфорсе* — одинаковый ответ на "пользователь не найден" и "пароль неверен".
* *Сессии не инвалидируются при смене пароля* — заложить метод `invalidateAllSessions(userId)` заранее, даже если UI смены пароля появится позже.

**Definition of Done.**
* Полный auth-flow покрыт API-тестами (register → login → me → logout).
* CSRF-тесты: мутация без заголовка отклонена с 403.
* Rate-limit-тест: 6-я попытка даёт 429.
* Web: кнопка logout работает, после 401 user возвращается на /login.
* Секреты не логируются (ревью `pino` redact-конфига).

**Оценка:** 2–3 дня.

## Milestone 2 — Profile & Metrics Catalog

**Цель.** Дать приложению «медицинский смысл»: профиль пациента (пол, дата рождения) нужен для расчёта референсных диапазонов, а каталог метрик — это справочник, из которого пользователь будет выбирать показатели при вводе измерений.

**Объём.**
* Модель `Profile` (one-to-one с `User`), enum `Sex`.
* API `GET/PUT /profile`, UI страницы просмотра и редактирования.
* Onboarding-редирект: если профиль не заполнен — ведём на форму.
* Модели каталога: `Metric`, `MetricSynonym`, `MetricAllowedUnit`, `ReferenceRange`.
* Сид-скрипт с ≈ 45 метриками из пяти категорий: гематология, биохимия, липиды, гормоны, витамины/минералы.
* Референсные диапазоны: половая стратификация (для гормонов, гемоглобина, ферритина), возрастная — где это клинически принято (детские нормы — задел, но в MVP основной фокус на взрослых).
* API каталога: список с поиском по name/synonym + пагинация, get-by-id, создание пользовательской метрики, переопределение референса.
* UI каталога: список с поиском, карточка метрики, диалог создания собственной, диалог переопределения диапазона.

**Результат.** В приложении есть «словарь анализов» с корректными нормами. Пользователь видит свой профиль и может его править.

**Зависимости.** Milestone 1 (нужен user-scope для кастомных метрик и профиля).

**Риски.**
* *Недостоверные референсы в сиде* — базовые справочные значения могут расходиться с рекомендациями конкретной лаборатории. Решаем через возможность override и явную формулировку в UI «стандартные референсы, уточняйте у лаборатории».
* *Раздутый сид* — легко закопаться в узкие субметрики. Держим MVP ≤ 50 метрик, остальное добавляем по мере запроса.
* *Несогласованные единицы* — один и тот же анализ приходит в mg/dL и mmol/L. `MetricAllowedUnit` + таблица конверсий решает, но нужно внимательно собрать её для сида.
* *Поиск по кириллице и синонимам* — SQLite `LIKE` без FTS не всегда удобен; на MVP хватает, но помечаем как кандидата на замену FTS5 позже.

**Definition of Done.**
* Сид идемпотентен: повторный запуск не дублирует данные.
* Поиск по каталогу находит метрику по русскому имени, английскому имени, синониму и коду.
* Переопределённые пользователем диапазоны не затираются при повторном сиде.
* Edit-профиль: при сохранении пустой dob/sex — валидация не пропускает.

**Оценка:** 3 дня.

## Milestone 3 — Measurements CRUD

**Цель.** Главный рабочий сценарий приложения: пользователь вносит результаты анализа за дату, связывает их с метриками из каталога, получает сохранённую запись с возможностью редактирования и удаления.

**Объём.**
* Модели `Measurement` (шапка записи: дата, заметка, user) и `MetricValue` (одно значение внутри записи: metric, value, unit).
* Полный CRUD API: create, list (с фильтрами по дате/метрике и пагинацией), get-by-id, update (замена набора значений), delete с каскадом на values.
* Сервер-side валидация: единица должна быть в `MetricAllowedUnit` выбранной метрики, значение > 0, дата не в будущем.
* Утилита конверсии единиц (двусторонняя) — используется при аналитике, не при сохранении (храним «как ввёл пользователь»).
* UI формы: шапка (дата, свободные заметки) + список динамических строк «метрика-значение-единица». Компонент `MetricSearchSelect` для выбора метрики.
* UI списка измерений: сгруппированные по дате, с превью первых 3–4 значений, бейджем «есть отклонения».
* UI детали измерения: полный состав + заметки + кнопки редактирования/удаления.
* Optimistic update при создании: запись сразу появляется в списке, потом синхронизируется.

**Результат.** Полноценный поток «записать — посмотреть — изменить — удалить», без которого приложение не имеет смысла.

**Зависимости.** Milestone 2 (нужны метрики), Milestone 1 (user-scope).

**Риски.**
* *Форма становится громоздкой при 10+ метриках* — решаем через компактное отображение (стек строк), возможность дублировать строку, автодополнение единицы последней использованной для этой метрики.
* *Дата в локальной зоне пользователя vs UTC в БД* — фиксируем: хранить как `DateTime` в UTC, но в валидации использовать пользовательскую timezone. Timezone берём из профиля (задел на будущее, в MVP — tz браузера).
* *Двойной ввод одной даты* — не блокируем, но выводим warning «на эту дату уже есть запись, объединить?» (опционально в MVP).

**Definition of Done.**
* Create + list + detail + update + delete покрыты API-тестами.
* Unit conversion покрыт юнит-тестами минимум для лидов (mg/dL↔mmol/L), гемоглобина (g/L↔g/dL), креатинина, глюкозы, витамина D.
* В UI форма валидируется в реальном времени, submit недоступен при ошибках.
* Удаление требует подтверждения.

**Оценка:** 3–4 дня.

## Milestone 4 — Attachments

**Цель.** Дать возможность прикреплять оригинал лабораторного отчёта: фото бланка или PDF-скан. Это не только архив, но и страховка — если пользователь введёт значение с ошибкой, можно вернуться к оригиналу.

**Объём.**
* Модель `Attachment` (связь с `Measurement`, filename, mime, size, path, createdAt).
* Абстракция `StorageProvider` с двумя методами (`put`, `get`, `delete`) и `LocalFsStorage` как первой реализацией. Заложено S3 на будущее.
* API: upload (multipart), retrieve (stream с access-check), delete.
* Ограничения: whitelist MIME (jpeg, png, webp, pdf), лимит 10 МБ на файл, 50 МБ суммарно на измерение.
* Web: компонент загрузки файла + нативный `capture=environment` для мобильной камеры; прогресс-бар, предпросмотр, удаление.
* Превью-галерея на странице измерения + lightbox-модал для увеличения изображения/открытия PDF.

**Результат.** К каждому измерению можно приложить до нескольких файлов, они показываются как миниатюры и открываются по клику.

**Зависимости.** Milestone 3.

**Риски.**
* *Забытый access-check* — пользователь мог бы через прямую ссылку достать чужие файлы. Сервер-side проверка `attachment.measurement.userId === req.user.id` — обязательна в тестах.
* *Большие фото с современных телефонов (5–10 МБ)* — лимит 10 МБ может быть тесноват, но иначе хостинг быстро раздуется. На будущее — клиентская ресайз/сжатие.
* *EXIF-данные* — удаляем при сохранении (геолокация, модель телефона — не нужны).
* *Сохранённые файлы остаются при удалении измерения* — каскад должен чистить и физические файлы, тест обязателен.

**Definition of Done.**
* Upload/retrieve/delete покрыты API-тестами, включая rejection-кейсы (403 чужому, 413 оверсайз, 415 неверный MIME).
* На мобильном Safari фронт вызывает камеру, на десктопе — обычный file picker.
* Lightbox закрывается по ESC и клику вне изображения.

**Оценка:** 2 дня.

## Milestone 5 — Chart & Analytics

**Цель.** Закрыть ключевой пользовательский запрос — смотреть динамику показателей во времени. Без графика приложение это просто архив записей.

**Объём.**
* API `GET /analytics/chart/:metricId` — возвращает временной ряд значений с привязкой к референсному диапазону на каждую дату (возраст пациента на момент измерения + пол → нужный `ReferenceRange`).
* API для overlay-режима: `GET /analytics/chart?metrics=...&normalize=true` — значения нормализуются как `% от середины референса` (100% = идеальная середина нормы), возвращается унифицированный ряд + единая полоса 80–120%.
* Фасад `<AnalyteChart>` в web: принимает нормализованные props `series: AnalyteSeries[]`, `referenceBand?`, `mode: 'single' | 'overlay'`. Внутри — реализация на Recharts, заменяемая без изменения вызывающего кода.
* Полоса референса (зелёная зона), метки точек с цветом по статусу (ниже/норма/выше), tooltip со значением, единицей, датой, статусом.
* Лента дат под графиком (из мокапа), клик по точке → переход на соответствующее измерение.
* Legend с возможностью скрыть/показать серии в overlay-режиме.
* Страница single-metric chart (маршрут `/metrics/:id`) и страница overlay (`/analytics`, мультиселект метрик).

**Результат.** Пользователь может смотреть тренд любого показателя и сравнивать несколько между собой.

**Зависимости.** Milestones 2, 3 (нужны и метрики с референсами, и накопленные данные).

**Риски.**
* *Разные единицы в истории одной метрики* — если пользователь сначала вводил mg/dL, потом mmol/L. Сервер-side конвертирует в «каноничную» единицу метрики перед подачей в график.
* *Референсный диапазон меняется со временем* (например, пациент стал взрослым) — полоса на графике должна быть не одной прямой, а ступенькой. В MVP допустимо показать полосу для «текущего возраста» и пометить в UI; полноценная «ступенька» — v1.1.
* *Графики на телефоне с ≥ 100 точек лагают* — decimation на клиенте при > 60 точках.
* *Абстракция над чартом без единого пользователя узнаёт рано о проблемах поздно* — валидируем интерфейс на single и overlay сразу в этой вехе, чтобы не пришлось переделывать при миграции на ECharts.

**Definition of Done.**
* Single-metric chart рисуется для любой метрики, у которой ≥ 2 измерения.
* Overlay рисуется для ≤ 6 метрик одновременно, с нормализацией.
* Клик по точке переходит на measurement-detail.
* Тест (RTL + data-testid) подтверждает, что при подмене реализации `AnalyteChart` на заглушку страницы не падают — это проверка фасада.

**Оценка:** 3–4 дня.

## Milestone 6 — Export, Import, Dashboard

**Цель.** Закрыть две темы: (а) пользователь должен владеть своими данными и уметь их забрать в любой момент, (б) при первом входе в приложение нужен обзорный экран, а не сразу список измерений.

**Объём.**
* Export: JSON (полный дамп всей пользовательской структуры + прикрепления в виде списка ссылок на файлы в архиве) и CSV (плоская таблица «дата — метрика — значение — единица — заметка»).
* Import: round-trip из JSON-экспорта. В MVP — только с dry-run превью: сколько измерений будет добавлено, сколько конфликтов. Слияние конфликтов — v1.1.
* Dashboard (home-экран): сетка карточек по закреплённым метрикам с последним значением, статусом (цвет), датой последнего измерения, микро-спарклайном (опционально).
* Список последней активности (3–5 последних измерений).
* Quick-actions: «Новое измерение», «Посмотреть каталог», «Экспорт».

**Результат.** При заходе в приложение пользователь сразу видит самое важное. Может забрать все данные одним файлом.

**Зависимости.** Milestones 3, 5 (хочется видеть на dashboard статус и, опционально, спарклайн).

**Риски.**
* *Большие экспорты валят память* — streaming-export с постраничной выборкой из БД; тест с 5 000 измерений.
* *Import может затереть данные* — только add-mode в MVP, с явным dry-run и текстовым подтверждением (например, ввод слова «импортировать»).
* *Dashboard без закреплённых метрик выглядит пусто для нового пользователя* — выводим sensible defaults (например, популярные метрики, показанные как call-to-action «Добавьте первое измерение»).

**Definition of Done.**
* Round-trip export → import на тестовом дампе даёт идентичные данные (проверка через `deep-equal` в тесте).
* CSV открывается без ошибок в Excel/Numbers/LibreOffice (разделитель — запятая, кавычки для заметок).
* Dashboard рендерится меньше чем за 500 мс на мокнутых 20 метриках (performance-тест).

**Оценка:** 2 дня.

## Milestone 7 — Polish, PWA, Release

**Цель.** Превратить работающий прототип в продукт, который не стыдно поставить на прод и пользоваться самому ежедневно.

**Объём.**
* PWA: manifest, иконки, service worker (workbox) с кэшированием app-shell, offline-страница.
* Установка на home screen (iOS/Android/desktop), проверка в реальных браузерах.
* Dark mode: система через CSS-переменные, переключатель, сохранение выбора в профиле.
* Empty states на всех экранах (каталог, измерения, dashboard, графики).
* Глобальный error boundary + toast-нотификации для сетевых ошибок.
* Accessibility: focus trap в модалках, aria-labels, контраст, keyboard navigation формы создания измерения.
* Performance: route-level code splitting, lazy-loading изображений, дебаунс поиска в каталоге.
* Критические e2e-тесты (playwright или vitest + RTL): auth-flow, создание измерения, просмотр графика.
* Инфраструктура прода: `docker-compose.prod.yml` + Caddyfile с auto-HTTPS; скрипты `backup.sh`/`restore.sh`.
* Документация: пользовательский мануал (RU) + runbook для себя.
* Релиз: версия, changelog, тег `v0.1.0`.

**Результат.** Приложение развёрнуто на реальном домене, используется самим автором, готово к dogfooding.

**Зависимости.** Всё предыдущее.

**Риски.**
* *PWA на iOS — много подводных камней* (ограничения Service Worker, push, add-to-home-screen UX). Держим требования минимальными: установка и offline app-shell, без push.
* *Caddyfile + reverse proxy + cookies с `Secure`* — нужно проверить заголовки `X-Forwarded-*` и правильную работу cookies за прокси. Есть шанс потратить полдня на отладку.
* *Dark mode ломает график* — проверяем палитру на всех 5 категориях метрик, на точках out-of-range, на полосе референса.
* *Релиз откладывается из-за «ещё чуть-чуть отполирую»* — фиксируем таймбокс вехи 3 дня и выпускаем даже с известными minor-баги, занося их в `v0.1.1`.

**Definition of Done.**
* Приложение установлено на домашний сервер, доступно по HTTPS.
* Можно установить на iPhone как PWA и открыть в offline-режиме.
* `backup.sh` создаёт архив, `restore.sh` успешно восстанавливает в чистый контейнер (проверено).
* Changelog отражает все крупные фичи v0.1.
* Тег `v0.1.0` создан, CI собрал и запушил образы.

**Оценка:** 3 дня.

## Version 1.0 — Stabilization

**Цель.** Снять с полки «v0.1 MVP» и через недели реального использования довести до уровня «я этим пользуюсь каждый день и не замечаю багов».

**Объём.**
* Повышение покрытия тестами: API > 80% строк, web — все критичные пути.
* Playwright-сьют с кросс-браузерным прогоном в CI.
* Ревизия индексов БД по реальным query-планам (`EXPLAIN` на накопленных данных).
* Оптимизация графика для длинных серий (> 100 точек).
* Bug-fix-стрим: всё, что всплыло за две недели dogfooding.
* Operations: healthcheck-эндпоинт, log rotation, runbook с инцидентными сценариями (БД повреждена, диск заполнился, Caddy не обновил сертификат).
* Документ-спецификация замороженная, зафиксирован контракт публичного API.

**Результат.** v1.0.0 — стабильная версия, на которой можно разворачивать приложение для родственников.

**Зависимости.** v0.1.0 + реальное использование ≥ 2 недель.

**Риски.**
* *Слишком большой фикс-лист, v1.0 не заканчивается* — жёсткий критерий: переносим все non-blocker в v1.1.
* *Миграции БД в stabilization-фазе* — стараемся избегать, но если нужно — обязательно с backup-then-migrate runbook.

**Definition of Done.**
* Все open P0/P1 issues закрыты.
* Coverage-пороги проходят в CI.
* Playwright-сьют зелёный в двух браузерах.
* `v1.0.0` тег + обновлённый changelog.

**Оценка:** 7–10 рабочих дней растянуто на 2–3 календарные недели (параллельно с использованием).

## Version 1.1 — Quality of Life

**Цель.** Небольшие удобства, которые не делают приложение концептуально богаче, но убирают трение в ежедневном сценарии.

**Объём.**
* Keyboard shortcuts на форме измерения (enter — новая строка, cmd+s — сохранить).
* Bulk-операции: удалить / экспортировать несколько измерений.
* Print-friendly вид страницы измерения (для приёма у врача).
* Summary-страница: агрегаты за период (среднее / медиана / min / max за квартал/год) с мини-графиками.
* Локализованный date-picker (русские названия месяцев, первый день недели — ПН).
* Возможность прикрепить PDF как attachment без парсинга (OCR — v2.0).
* Ступенчатая референсная полоса на графике (разные диапазоны для разных возрастов).
* Внутренний рефактор: вынос chart-фичи в `packages/feature-chart`.

**Результат.** Приложение становится удобнее в «потом посмотрю» кейсах: распечатать на приём, быстро добавить серию измерений с клавиатуры.

**Зависимости.** v1.0.0.

**Риски.**
* *Summary считается на лету и тормозит* — нужен кэш или материализованное представление; в MVP-варианте обсчёт на клиенте из уже загруженных данных.
* *Ступенчатая полоса референса ломает legacy-графики* — делаем feature-flag до окончания тестирования.

**Definition of Done.**
* Keyboard-flow проходит по форме без мыши от начала до сохранения.
* Печатная версия страницы измерения помещается на одну A4-страницу.

**Оценка:** 5–7 дней.

## Version 2.0 — OCR, Symptoms, Medications, Tags, Multi-patient

**Цель.** Превратить трекер анализов в персональный медицинский журнал: добавить симптомы, лекарства, возможность вести несколько пациентов (например, детей и родителей), автоматизировать ввод из лабораторных PDF.

**Объём.**
* Модель `Patient`: все данные начинают скопироваться по patient_id; существующие данные мигрируются как «Patient: default (вы)».
* Переключатель пациентов в header.
* Модели `Tag`, `Symptom`, `Medication` с соответствующими CRUD и связями с measurement/дневником.
* Дневник симптомов: оценка 1–5 по дате, свободный текст.
* Медикаменты: что, когда, в какой дозе, по какому расписанию; на графике — вертикальные метки «старт/стоп приёма».
* OCR-пайплайн: загружаешь PDF лабораторного отчёта → сервер запускает tesseract (или внешний API) → извлекает таблицу → показывает на confirm-экране → пользователь правит → сохраняется как measurement с attached PDF.
* Корреляционный чарт: график метрики с наложением симптомов или медикаментов (как rugplot или вторичная ось).

**Результат.** Приложение перестаёт быть только про анализы и превращается в полноценный медицинский журнал.

**Зависимости.** v1.0.0; желательно v1.1 (summary как база для корреляций).

**Риски.**
* *OCR — самый большой source of effort*. Русские PDF-бланки бывают разнородными: разные шрифты, сканы плохого качества. Ожидаемо тратим на OCR половину времени вехи, с риском, что первая версия работает только на 60% образцов. Решение: confirm-экран с ручной правкой — ошибки OCR не должны блокировать ввод.
* *Миграция на multi-patient ломает все API-контракты* (в путь добавляется patientId или берётся из заголовка/кука). Делаем миграцию одним большим PR, чтобы не жить во временном несогласованном состоянии.
* *Симптомы/лекарства — скользкая граница с «не медицинское устройство»*. Фиксируем позиционирование: это журнал, не диагност, никаких автоматических рекомендаций.

**Definition of Done.**
* Multi-patient миграция: старые данные доступны, новый пациент создаётся и изолирован.
* OCR на 5 тестовых PDF (разные лаборатории) извлекает ≥ 80% значений; остальное правится вручную.
* Корреляционный чарт рисует метрику + симптомы за тот же период.

**Оценка:** 3–4 недели (крупная веха, детализация в отдельном roadmap-подпункте ближе к старту).

## Version 3.0 — Sharing, Native, Lab API

**Цель.** Выйти за рамки одного устройства и одного пользователя: делиться выжимкой с врачом, работать как нативное приложение, подтягивать данные из лабораторий по API.

**Объём.**
* Расшаривание: read-only ссылки с expiry (24h / 7d / custom), выбор, какие метрики и за какой период попадают в публичный view.
* Публичная страница-«отчёт» для врача: только чтение, без возможности редактирования, с явным водяным знаком и источником.
* Native обёртки через Capacitor (iOS/Android): локальное хранилище через SQLite нативный, push-уведомления (напоминания про приём лекарств, про плановый анализ).
* Интеграции с лабораториями: provider-pattern — абстракция `LabProvider`, первые реализации под популярные локальные сети (Инвитро, Хеликс, Гемотест), через их API или через регулярный парсинг личного кабинета.

**Результат.** Приложение полноценно используется на телефоне без браузера, синхронизируется с лабораторией, позволяет быстро поделиться выдержкой с врачом.

**Зависимости.** v2.0.

**Риски.**
* *Публичные ссылки — privacy hot-spot*. Обязателен audit: expiry, отзыв ссылок, детальный лог обращений к ним.
* *Нативные приложения — отдельные SDLC* (подписи, сертификаты Apple, Google Play-review). Первая native-релиз займёт минимум 2 недели сверх разработки.
* *Lab API*: у большинства лабораторий нет публичного API, придётся делать браузерный парсинг личного кабинета → нестабильно, ломается при редизайне сайта лаборатории. Начинаем с одной и чётко коммуницируем «best effort».

**Definition of Done.**
* Share-link open в incognito работает, после expiry возвращает 410.
* Revocation: отзыв ссылки мгновенно делает её недействительной.
* Native-сборка запускается на физическом устройстве (iOS + Android).
* Minimum один LabProvider импортирует измерения без ручного ввода.

**Оценка:** 4–6 недель.
