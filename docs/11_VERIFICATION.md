# 11. Проверки работоспособности после коммитов

Короткий ответ: **да, это не только возможно, но и обязательная практика**. Без автоматических проверок любой проект такого размера разваливается уже на втором-третьем десятке коммитов. Причём именно **автоматика** делает её посильной для «не разбирающегося человека»: вы не читаете логи и не гоняете тесты руками — вы смотрите на один светофор рядом с коммитом.

Документ описывает трёхуровневую систему проверок: что срабатывает после каждого коммита, что перед вливанием в main, и какой ручной checklist делать после завершения вехи.

---

## Философия

1. **Красное не пропускаем.** Если хотя бы одна проверка упала — коммит/PR не вливается, пока не починим. Чинить проще сразу, чем через неделю, когда сверху уже 20 коммитов.
2. **Автоматика несёт 95% работы.** Человек нужен только для проверки «выглядит ли это нормально» — остальное делают линтер, типы, тесты, CI.
3. **Быстрые проверки — чаще, медленные — реже.** Лёгкое (форматирование, типы) — при каждом коммите. Тяжёлое (полные e2e, Docker-сборки) — при merge.
4. **Каждая проверка — с понятным вердиктом.** Зелёная галочка / красный крест. Не «warning», не «might fail».

---

## Три уровня проверок

```
┌──────────────────────────────────────────────────────┐
│  Уровень 1 — КАЖДЫЙ коммит (локально + CI)           │
│  → секунды, blocker: нельзя запушить сломанный код   │
├──────────────────────────────────────────────────────┤
│  Уровень 2 — merge в main (CI)                       │
│  → минуты, blocker: нельзя влить сломанный PR        │
├──────────────────────────────────────────────────────┤
│  Уровень 3 — конец вехи (человек)                    │
│  → 15–30 мин по чек-листу, вы убеждаетесь «работает» │
└──────────────────────────────────────────────────────┘
```

---

## Уровень 1 — проверки на каждом коммите

### Что проверяется локально (до того как коммит появится)

**Husky pre-commit hook** (запускается автоматически при `git commit`):

| Проверка | Что делает | Если упала |
|---|---|---|
| Prettier | Автоматически форматирует изменённые файлы | Безболезненно — просто перезаписывает код |
| ESLint | Ищет типичные ошибки: неиспользуемые переменные, потенциальные баги | Коммит блокируется с подсказкой «нужно починить» |
| TypeScript typecheck (инкрементальный) | Проверяет, что типы согласованы в изменённых файлах | Коммит блокируется |
| Commitlint | Проверяет, что сообщение коммита соответствует `feat(...): ...` | Коммит блокируется |

Это быстрые проверки — 2–10 секунд. Если всё зелёное, коммит попадает в историю.

**Husky pre-push hook** (запускается при `git push`):

| Проверка | Что делает |
|---|---|
| Полный typecheck | Проверяет всю кодовую базу, а не только изменённые файлы |
| Unit-тесты | Прогоняет юнит-тесты (примерно 1–2 минуты на MVP) |

Если что-то падает — push блокируется, и вы либо чините, либо делаете `git push --no-verify` (не рекомендуется).

### Что проверяется в CI (после пуша на GitHub)

**GitHub Actions workflow** (файл `.github/workflows/ci.yml`) запускается при каждом пуше и каждом PR:

| Job | Что проверяет |
|---|---|
| `lint` | ESLint + Prettier на всём репо |
| `typecheck` | `tsc --noEmit` на всех рабочих пакетах (web, api, shared) |
| `test:api` | Юнит + integration тесты API (с временной SQLite-БД) |
| `test:web` | Юнит + component тесты React (vitest + RTL) |
| `build` | Сборка production-версии web и api — если не собралось, ошибка компиляции |
| `migrate:check` | На пустой БД прогоняет все миграции + rollback |

Это **5–10 минут**. Результат отображается рядом с коммитом на GitHub:

```
✓ lint           2s
✓ typecheck      45s
✓ test:api       1m 20s
✓ test:web       2m 15s
✓ build          3m 30s
✓ migrate:check  25s
```

Если хоть одна красная — вы видите её в списке, кликаете и читаете лог.

### Как это помогает «не разбирающемуся человеку»

**Вы не читаете логи, пока всё зелёное.** Смотрите на коммит в GitHub — видите ✓. Всё.

**Когда что-то красное** — вы кликаете на красный шаг и видите, обычно, что-то вроде:
```
apps/web/src/components/MetricForm.tsx(42,10): error TS2339:
Property 'units' does not exist on type 'Metric'.
```
Это значит: «на строке 42 файла MetricForm.tsx используется поле `units`, но оно не объявлено в типе Metric». Это уже понятно — либо переименовать, либо добавить поле. Claude Code или любой другой ИИ-ассистент по такому сообщению починит за один вопрос.

**Правило для вас**: никогда не мерджите и не пушите в main коммиты с красным CI. Если какая-то проверка падает постоянно и непонятно почему — это чаще всего баг в самой проверке (флаки-тест), и такие вещи нужно прибивать в первый же день.

## Уровень 2 — проверки при merge в main

На этом уровне добавляются более тяжёлые, но и более ценные проверки. Запускаются при открытии Pull Request и ещё раз перед merge.

| Проверка | Что делает | Зачем |
|---|---|---|
| Всё из уровня 1 | — | base line |
| Docker build | Собирает образ api и web через `Dockerfile` | Ловит проблемы сборки, которые не видно локально |
| Playwright e2e smoke | Поднимает приложение в Docker и проходит 5–8 ключевых сценариев: логин, создание измерения, просмотр графика, экспорт | Ловит ошибки интеграции front↔back, которые не видит юнит-тест |
| Code coverage report | Измеряет % покрытия тестами и пишет комментарий в PR | Даёт видеть, когда вы пишете много кода без тестов |
| Bundle size check | Сравнивает размер бандла web с main | Предупреждает, если вы случайно затащили тяжёлую либу |
| Security audit | `pnpm audit` + `trivy` на Docker-образ | Ловит известные CVE в зависимостях |

Это 10–20 минут, но прогоняется только при PR — не на каждый коммит.

**Главное для вас** — полоса зелёных галочек внизу PR, перед кнопкой «Merge». Если полоса зелёная — можно сливать с высокой уверенностью, что ничего не сломалось.

## Уровень 3 — ручной smoke-checklist после вехи

Автоматика не ловит две категории проблем:
* **UX-баги**: кнопка работает, но находится в неправильном месте; чарт рисуется, но легенда заходит на ось.
* **Совокупные проблемы**: все компоненты по отдельности работают, но вместе создают странный опыт (например, после создания измерения не обновляется dashboard).

Поэтому в конце каждой вехи — **10–30 минут вручную** пройтись по приложению по заранее подготовленному чек-листу. Это делается один раз, не после каждого коммита.

### Пример чек-листа для Milestone 1 (Auth)

```
[ ] 1. Открыть /register в новом окне инкогнито
[ ] 2. Зарегистрироваться с email + паролем
[ ] 3. Увидеть редирект на home (или на профиль при первом заходе)
[ ] 4. Обновить страницу (F5) — остаться залогиненным
[ ] 5. Открыть DevTools → Application → Cookies
      → увидеть cookie "sid" с флагами HttpOnly, Secure (в проде)
[ ] 6. Нажать logout → вернуться на /login
[ ] 7. Попытаться открыть /dashboard → редирект на /login
[ ] 8. Войти со случайным паролем → сообщение об ошибке,
      но НЕ "пользователь не найден" (защита от enumeration)
[ ] 9. Попытаться войти 6 раз подряд с неверным паролем
      → на 6-й раз сообщение "слишком много попыток, подождите"
```

Если все 9 пунктов зелёные — Milestone 1 закрыт.

### Пример чек-листа для Milestone 3 (Measurements)

```
[ ] 1. Создать новое измерение: дата вчерашним числом
[ ] 2. Добавить 3 строки с разными метриками (гемоглобин, ALT, TSH)
[ ] 3. Сохранить → увидеть его в списке на сегодня
[ ] 4. Открыть детали → все 3 значения на месте
[ ] 5. Редактировать → изменить значение → сохранить → значение обновилось
[ ] 6. Удалить → запись исчезла из списка
[ ] 7. Попытаться ввести дату в будущем → валидация не пропускает
[ ] 8. Попытаться ввести отрицательное значение → валидация не пропускает
[ ] 9. Открыть приложение на телефоне (или в Chrome DevTools device emulation)
      → форма удобна на узком экране, не требует горизонтального скролла
[ ] 10. Создать измерение, не заполнив единицу → подсказка «выберите единицу»
```

Чек-лист для каждой вехи пишется в рамках той же вехи (5–10 минут работы) и хранится в `docs/checklists/milestone-N.md`. К концу проекта у вас накапливается полный «регрессионный лист» на 80–120 пунктов — его полезно прогонять перед каждым мажорным релизом.

### Кто пишет чек-лист

Автор вехи (вы). Это занимает 5–10 минут в конце вехи: открываете свои user stories из `02_USER_STORIES.md` для закрытых в веху историй и превращаете каждый acceptance criterion в пункт чек-листа.

## Что входит в «минимальный набор», без которого не стартовать

Это не «nice to have», это фундамент. Если на него не заложить время в Milestone 0 — вы поймаете первую ошибку только когда она попадёт в прод:

* ESLint + Prettier, настроенные одинаково в IDE и в pre-commit.
* TypeScript в strict-режиме (`"strict": true` в `tsconfig`).
* CI на GitHub Actions с минимум тремя джобами: lint, typecheck, test.
* Husky с pre-commit хуком.
* Хотя бы один end-to-end smoke-тест (например, логин + создание измерения) на Playwright — это ваш «проверка пульса» при каждом PR.

Если вы строите приложение в одиночку и считаете, что «тесты замедляют» — опыт показывает обратное: в проекте с ~180 коммитами без автоматики к середине пути теряется столько времени на ручную проверку, что писать тесты было бы в 2–3 раза быстрее.

## Как это выглядит в рабочем цикле

**Обычный день разработки:**

1. Открываете issue из плана коммитов (например, «feat(api): POST /measurements»).
2. Пишете код. Ошибаетесь. Линтер подсвечивает в IDE.
3. Запускаете `pnpm test --watch` рядом — тест гоняется при каждом сохранении.
4. `git add + git commit -m "feat(api): POST /measurements"` — husky прогоняет prettier/eslint/typecheck/commitlint за 5 секунд.
5. `git push` — pre-push прогоняет полные тесты за минуту.
6. На GitHub открываете PR — CI прогоняет полный суит за 10 минут.
7. Зелёный → merge. Красный → кликаете красную галочку, читаете, чините, пушите ещё коммит.

**После закрытия вехи:**

1. CI зелёный по всем коммитам вехи.
2. Открываете `docs/checklists/milestone-N.md`, проходите пункты в приложении.
3. Если все пункты зелёные — тегируете веху (например, `milestone-3-complete`) и переходите к следующей.
4. Если какой-то пункт красный — создаёте issue, чините, ретестируете.

## Когда имеет смысл вложиться в ещё более сильные проверки

По мере взросления проекта и ближе к v1.0:

* **Visual regression** (Chromatic, Percy) — screenshots компонентов сравниваются с baseline. Ловит ломки вёрстки, которые юнит-тесты не видят.
* **Contract tests** для API — запросы от web зафиксированы как снапшоты, API падает, если ответ изменил форму.
* **Performance budgets** в Lighthouse CI — ошибка, если страница загружается дольше N мс.
* **Preview deployments** — каждый PR автоматически разворачивается на эфемерный домен, и вы можете кликнуть по приложению своими руками ещё до merge.

Но всё это — на потом. На MVP достаточно того, что описано в уровнях 1–3.

---

## TL;DR

> Да, проверять работоспособность после каждого коммита не только можно, но и **принципиально**. Для «не разбирающегося человека» это сводится к одному правилу: **не игнорировать красные галочки**. Всё остальное (что именно запускать, когда, как читать результаты) — это набор настроек, который делается один раз в Milestone 0 и дальше работает сам.

Следующий шаг после согласования: в `09_COMMIT_PLAN.md` в Milestone 0 добавить отдельные коммиты на настройку husky-хуков и CI-workflow, а в конце каждой вехи — коммит `docs(checklist): milestone-N manual checks`.
