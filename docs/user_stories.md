# 02. Пользовательские сценарии

Документ описывает пользовательские истории (user stories) с критериями приёмки (acceptance criteria) и детальные end-to-end сценарии использования. Для каждой истории указан идентификатор вида `US-XX`, который используется в задачах роадмапа и в коде (комментарии, тесты).

## Роли

- **Пациент** — основной пользователь, ведёт записи о себе.
- **Администратор** — тот, кто развернул инсталляцию (может совпадать с пациентом).
- В MVP отдельного «врача» нет — врач получает PDF-отчёт и не имеет учётной записи в системе.

## Эпик A. Аутентификация и профиль

### US-01. Регистрация

**Как** новый пользователь,
**я хочу** создать учётную запись с e-mail и паролем,
**чтобы** начать вести свою историю анализов.

**Acceptance criteria:**
- Форма запрашивает: e-mail, пароль, подтверждение пароля, имя, пол, дату рождения.
- E-mail валидируется по RFC 5322; ошибка при невалидном.
- Пароль минимум 10 символов; валидируется сила (минимум 3 из 4 классов: буквы нижнего, верхнего регистра, цифры, спецсимволы).
- Подтверждение пароля должно совпадать; ошибка при расхождении.
- Если e-mail уже занят — сообщение «пользователь с таким e-mail уже существует», без утечки временем ответа.
- После успешной регистрации пользователь автоматически авторизуется и попадает на главный экран.
- В БД пароль хранится только как bcrypt-хэш (cost ≥ 12).
- Дата рождения должна быть в прошлом и не более 120 лет назад.

### US-02. Вход

**Как** зарегистрированный пользователь,
**я хочу** войти в систему по e-mail и паролю,
**чтобы** получить доступ к своим данным.

**Acceptance criteria:**
- Форма запрашивает e-mail и пароль.
- При неверных данных — общее сообщение «неверный e-mail или пароль» (без раскрытия, что именно не так).
- При 5 неудачных попытках подряд с одного IP за 15 минут — блокировка на 15 минут с 429 Too Many Requests.
- При успешном входе создаётся запись в таблице Session, `sid` выставляется в cookie httpOnly + Secure + SameSite=Strict.
- Cookie имеет Max-Age = 30 дней.
- Чекбокс «запомнить меня» отсутствует: по умолчанию сессия долгоживущая, выход инвалидирует её.
- После входа пользователь попадает на экран списка замеров.

### US-03. Выход

**Как** авторизованный пользователь,
**я хочу** выйти из системы,
**чтобы** завершить сессию (особенно на чужом устройстве).

**Acceptance criteria:**
- Кнопка «Выйти» доступна в меню пользователя.
- По клику — запись в Session удаляется, cookie очищается, пользователь перенаправляется на экран входа.

### US-04. Смена пароля

**Как** авторизованный пользователь,
**я хочу** сменить пароль,
**чтобы** обеспечить безопасность аккаунта.

**Acceptance criteria:**
- Форма запрашивает: текущий пароль, новый пароль, подтверждение нового пароля.
- Проверяется текущий пароль; при ошибке — сообщение.
- Валидация нового пароля аналогична US-01.
- При успешной смене все активные сессии, кроме текущей, инвалидируются (записи из Session удаляются).
- Пользователь видит уведомление «пароль изменён».

### US-05. Редактирование профиля

**Как** авторизованный пользователь,
**я хочу** изменить имя, пол или дату рождения,
**чтобы** корректно отражать мои персональные данные (например, после юридической смены).

**Acceptance criteria:**
- Форма редактирования профиля доступна в разделе настроек.
- Изменение пола/даты рождения пересчитывает референсы для всех будущих отображений; уже сохранённые значения не меняются.
- Отображается предупреждение: «изменение пола или даты рождения повлияет на расчёт референсных диапазонов».

## Эпик B. Справочник показателей

### US-06. Просмотр списка показателей

**Как** авторизованный пользователь,
**я хочу** видеть справочник показателей,
**чтобы** понять, что я могу заносить, и найти нужный мне показатель.

**Acceptance criteria:**
- Раздел «Показатели» доступен из главного меню.
- Отображает предзагруженные показатели + мои пользовательские.
- Поиск по наименованию и синонимам (гемоглобин / Hb / HGB).
- Фильтр по категории (ОАК, биохимия, гормоны, витамины и т.д.).
- Для каждого показателя: наименование, единица, референс для моего профиля (с учётом пола/возраста).

### US-07. Добавление пользовательского показателя

**Как** авторизованный пользователь,
**я хочу** добавить показатель, которого нет в справочнике,
**чтобы** вести его историю наравне с остальными.

**Acceptance criteria:**
- Форма запрашивает: наименование, единицу, категорию (из предустановленных или новую), референс min/max.
- Валидация: все поля обязательны; min < max; единица выбирается из справочника единиц или вводится вручную.
- После создания показатель доступен в автокомплите при внесении замеров.
- Удалить пользовательский показатель можно только если он не используется ни в одном значении.

### US-08. Переопределение референса «для себя»

**Как** авторизованный пользователь,
**я хочу** переопределить референс для конкретного показателя,
**чтобы** он соответствовал рекомендациям моего врача или особенностям моей ситуации.

**Acceptance criteria:**
- В карточке показателя — кнопка «Переопределить референс».
- Форма запрашивает min/max и опционально комментарий (например, «по рекомендации эндокринолога»).
- После сохранения мой переопределённый референс используется во всех графиках и отображениях вместо дефолтного.
- Возможность вернуть референс к дефолту кнопкой «Сбросить».

## Эпик C. Внесение замеров

### US-09. Создание замера

**Как** авторизованный пользователь,
**я хочу** внести результаты анализа,
**чтобы** они были сохранены в истории.

**Acceptance criteria:**
- Кнопка «+ Новый замер» на главном экране.
- Форма запрашивает: дату замера (по умолчанию — сегодня), произвольное количество значений (показатель + число + единица), заметку, вложения.
- Выбор показателя — через автокомплит по справочнику; показатель подставляет свою единицу (можно изменить).
- При вводе значения система мгновенно показывает флаг: ниже нормы / в норме / выше нормы (на основе референса профиля).
- Заметка — произвольный текст, maxlength 5000 символов.
- Можно прикрепить до 10 файлов на один замер; каждый ≤ 10 МБ; допустимые типы: PDF, JPG, JPEG, PNG, HEIC.
- После сохранения — переход на карточку замера.
- Если пользователь закрывает страницу без сохранения — подтверждение «несохранённые изменения будут потеряны».

### US-10. Редактирование замера

**Как** автор замера,
**я хочу** исправить ошибку в дате, значении, единице или заметке,
**чтобы** данные оставались достоверными.

**Acceptance criteria:**
- В карточке замера — кнопка «Редактировать».
- Открывается та же форма, что и для создания, предзаполненная.
- Можно добавить/удалить значения, добавить/удалить вложения.
- При сохранении фиксируется `updatedAt`; история изменений не ведётся в MVP.

### US-11. Удаление замера

**Как** автор замера,
**я хочу** удалить замер,
**чтобы** убрать ошибочно внесённые данные.

**Acceptance criteria:**
- В карточке замера — кнопка «Удалить» с подтверждением.
- Модальное окно: «Удалить замер от [дата]? Будут удалены также все [N] вложений. Действие необратимо».
- После подтверждения: замер, значения и вложения удаляются (каскад), файлы удаляются с диска.
- Пользователь перенаправляется на список замеров.

### US-12. Прикрепление файла

**Как** автор замера,
**я хочу** прикрепить PDF-бланк или фото результата,
**чтобы** сохранить первоисточник.

**Acceptance criteria:**
- В форме замера — кнопка с иконкой «прикрепить» (по макету — круглая кнопка слева от поля ввода).
- При клике — три варианта: «Файл», «Фото», «Ввести вручную» (последнее фокусирует поле ввода).
- «Файл» открывает системный файл-пикер; допускаются PDF, JPG, JPEG, PNG, HEIC; размер ≤ 10 МБ.
- «Фото» на мобильном — открывает камеру; на десктопе — поведение совпадает с «Файл».
- Загрузка идёт с прогресс-баром; при ошибке — понятное сообщение.
- После загрузки файл появляется в списке вложений с превью (для изображений) или иконкой (для PDF).

## Эпик D. Просмотр и аналитика

### US-13. Список замеров

**Как** авторизованный пользователь,
**я хочу** видеть все мои замеры в хронологическом порядке,
**чтобы** быстро находить нужный.

**Acceptance criteria:**
- Главный экран отображает список замеров от самого свежего к самому старому.
- Каждый элемент списка: дата, количество значений, короткая превью-строка (первые показатели с отклонениями, «+N ещё»), пиктограмма наличия вложений.
- Пагинация по 50 записей; автоподгрузка при скролле.
- Фильтр по диапазону дат.
- Фильтр по наличию показателя (подсвечиваются замеры, где есть выбранный показатель).
- Клик по элементу — переход в карточку замера.

### US-14. Карточка замера

**Как** авторизованный пользователь,
**я хочу** видеть все детали одного замера,
**чтобы** понимать полную картину.

**Acceptance criteria:**
- Заголовок: дата замера, кнопки «Редактировать» и «Удалить».
- Блок значений: таблица «Показатель — Значение — Единица — Норма — Флаг отклонения».
- Для каждого значения — цветовой индикатор: красный (выше/ниже нормы), зелёный (в норме).
- Блок «Заметка»: текст заметки.
- Блок «Вложения»: галерея превью. Клик по превью открывает файл в модальном окне (встроенный PDF-ридер / просмотр изображения).
- Навигация «← Предыдущий замер / Следующий замер →» по стрелкам клавиатуры и свайпами на мобильном.

### US-15. График одного показателя

**Как** авторизованный пользователь,
**я хочу** видеть динамику выбранного показателя во времени,
**чтобы** понять тренд.

**Acceptance criteria:**
- Экран «Графики», выбор показателя из автокомплита.
- Отображается линия с точками — по X реальная шкала дат (не равномерная), по Y — значения.
- Фон содержит референсную полосу (цвет — зелёный с прозрачностью).
- Точки вне нормы подсвечиваются (красный край).
- Между соседними точками отображаются интервалы в днях (как на макете: «7 дней», «15 дней»).
- Tooltip при наведении показывает дату, значение, отклонение от нормы.
- Клик по точке — открывает карточку соответствующего замера.
- Переключатель периода: 3 мес / 6 мес / 1 год / всё время.
- Переключатель линии/столбцов (bar) опционально.

### US-16. Наложение нескольких показателей

**Как** авторизованный пользователь,
**я хочу** наложить на один график несколько показателей,
**чтобы** увидеть их взаимосвязь.

**Acceptance criteria:**
- В режиме графика — чекбоксы «Добавить слой» со списком часто используемых показателей.
- При выборе ≥ 2 показателей значения нормализуются: каждое значение переводится в «% от середины референса» (100% = середина нормы).
- Референсная полоса превращается в единую зону 80–120% (или ±% от середины, равные ширине референса каждого показателя — опция визуализации).
- Линии разных цветов (цвета задаются детерминированно по показателю).
- Легенда сверху; клик по легенде включает/выключает линию.
- Tooltip показывает оригинальное значение каждого показателя, не нормализованное.

### US-17. Кликабельный тайм-лайн замеров

**Как** пользователь на экране графика,
**я хочу** кликнуть на дату в нижней «полоске замеров»,
**чтобы** быстро открыть детали этого замера.

**Acceptance criteria:**
- Под графиком расположена горизонтальная полоса с отметками дат (как на макете: «датаконтроль»).
- Каждая отметка кликабельна.
- Клик — открывает карточку замера в выдвижной панели (drawer) или переходит на страницу замера (desktop).
- На карточке видно всю заметку и вложения этого замера.

## Эпик E. Экспорт

### US-18. JSON/CSV бэкап

**Как** авторизованный пользователь,
**я хочу** скачать полный бэкап своих данных,
**чтобы** иметь страховку и возможность мигрировать.

**Acceptance criteria:**
- Раздел «Экспорт» → кнопка «Полный бэкап».
- Система генерирует ZIP-архив: `backup-YYYY-MM-DD.zip`, содержащий:
  - `data.json` — полная выгрузка (пользователь, профиль, замеры, значения, показатели, референсы, заметки, метаданные вложений).
  - `data.csv` — плоский CSV со значениями для анализа в Excel/Sheets.
  - `attachments/` — папка со всеми файлами вложений, имена как в системе.
  - `README.txt` — краткая инструкция по структуре.
- Для больших архивов — потоковая генерация без загрузки всего в память.
- Файл отдаётся с правильным Content-Type и Content-Disposition.

### US-19. PDF-отчёт для врача

**Как** авторизованный пользователь,
**я хочу** сгенерировать PDF-отчёт за выбранный период,
**чтобы** показать его врачу на приёме.

**Acceptance criteria:**
- Раздел «Экспорт» → «Отчёт для врача».
- Форма: диапазон дат, выбор показателей (по умолчанию — все с > 1 значением в периоде).
- Генерируется PDF с:
  - Титульная страница: имя пациента, возраст, период, дата генерации.
  - Сводная таблица: показатель × даты → значения (с флагами отклонения).
  - Секция для каждого показателя с графиком динамики.
  - Приложение с заметками по каждому замеру.
  - Подвал каждой страницы: «Сгенерировано HealthTracker. Не является медицинским заключением».
- Отчёт скачивается как `report-YYYY-MM-DD.pdf`.

## Эпик F. Административные задачи

### US-20. Первый запуск инсталляции

**Как** администратор,
**я хочу** развернуть приложение одной командой,
**чтобы** начать использовать его.

**Acceptance criteria:**
- После `docker compose up -d` поднимаются контейнеры web, api, db, caddy.
- При первом старте api автоматически применяет миграции Prisma.
- При первом старте api загружает seed-каталог показателей (идемпотентно).
- Caddy автоматически получает Let's Encrypt сертификат (если DOMAIN в .env задан).
- В логах api при успешном старте — строка «Ready on :3000».
- Экран регистрации доступен по HTTPS.

### US-21. Ручной бэкап БД

**Как** администратор,
**я хочу** создать резервную копию БД командой,
**чтобы** застраховаться от потерь.

**Acceptance criteria:**
- Команда `docker compose exec api pnpm backup:create` создаёт файл `backups/backup-YYYY-MM-DD-HHMM.tar.gz` с дампом БД и копией папки storage.
- Бэкап создаётся с правильными правами доступа.
- В логах — размер итогового файла.

### US-22. Восстановление из бэкапа

**Как** администратор,
**я хочу** восстановить инсталляцию из бэкапа,
**чтобы** вернуть данные после сбоя.

**Acceptance criteria:**
- Команда `docker compose exec api pnpm backup:restore <path>` применяет указанный бэкап.
- Перед восстановлением — подтверждение (`--yes` флаг для скриптового режима).
- Текущая БД и storage заменяются содержимым бэкапа.
- После восстановления приложение перезапускается автоматически.

### US-23. Обновление версии

**Как** администратор,
**я хочу** обновить приложение до новой версии,
**чтобы** получить улучшения и фиксы.

**Acceptance criteria:**
- `git pull && docker compose pull && docker compose up -d --build` обновляет контейнеры.
- Миграции Prisma применяются автоматически при старте api.
- Если миграция не-обратно-совместимая — в логах явное предупреждение, рекомендация сделать бэкап перед обновлением.

## End-to-End сценарии

Детальные пошаговые сценарии, которые должны работать без сбоев. Используются как база для E2E-тестов.

### Сценарий 1. Первый день пользователя

1. Пациент открывает URL инсталляции в браузере телефона.
2. Видит экран «Вход / Регистрация», нажимает «Регистрация».
3. Заполняет форму: e-mail `anna@example.com`, пароль, имя `Анна`, пол `женский`, дата рождения `1990-05-15`. Нажимает «Создать аккаунт».
4. Попадает на пустой экран списка замеров с подсказкой «Пока нет ни одного замера. Добавьте первый».
5. Нажимает «+ Новый замер».
6. Форма: дата `сегодня`, добавляет первое значение: начинает вводить «гем…», выбирает «Гемоглобин (HGB)» из автокомплита, единица подставилась `г/л`, вводит `125`. Система мгновенно показывает флаг «в норме» (для женщины 35 лет референс 117–155 г/л).
7. Добавляет второе значение: «ТТГ», единица `мкМЕ/мл`, вводит `4.8`. Система показывает «в норме», но близко к верхней границе.
8. Пишет заметку: «Сдавала утром натощак. Последние 2 недели немного устаёт».
9. Нажимает иконку прикрепления, выбирает «Фото», снимает бланк анализа. Файл загружается, появляется превью.
10. Нажимает «Сохранить». Попадает на карточку замера, видит сохранённые данные.

**Ожидаемый результат**: все данные сохранены в БД, файл сохранён в `storage/{userId}/{measurementId}/{hash}.jpg`, ответ 201.

### Сценарий 2. Просмотр тренда через полгода

1. Пациент уже полгода вносит замеры (7 замеров, гемоглобин в каждом).
2. Открывает раздел «Графики», выбирает «Гемоглобин».
3. Видит линию с 7 точками, реальная шкала дат (интервалы отображаются: 7, 15, 30 дней и т.д.).
4. Видит, что последние 3 точки идут вниз, последняя — ниже референсной полосы (подсвечена красным).
5. Наводит на последнюю точку — tooltip показывает «12 октября, 108 г/л, ниже нормы на 8%».
6. Кликает по точке в нижней полоске «датаконтроль» → открывается карточка соответствующего замера.
7. Читает свою заметку того дня: «болела неделю, ела плохо».

**Ожидаемый результат**: данные корректны, tooltip и цветовые акценты соответствуют значениям, клик открывает правильный замер.

### Сценарий 3. Подготовка к визиту к врачу

1. Пациент идёт на приём через 2 дня, хочет подготовить отчёт.
2. Открывает «Экспорт» → «Отчёт для врача».
3. Выбирает период «последние 12 месяцев». Оставляет «все показатели».
4. Нажимает «Сгенерировать». Через 5–10 секунд скачивается PDF.
5. Открывает PDF: видит титульную страницу с ФИО и возрастом, сводную таблицу за 12 месяцев с цветовыми флагами, графики по каждому показателю, заметки.
6. Распечатывает или отправляет врачу в мессенджер.

**Ожидаемый результат**: PDF читаем, не содержит ошибок вёрстки, графики отображаются с референсными полосами.

### Сценарий 4. Исправление ошибки ввода

1. Пациент заметил, что полгода назад ввёл значение ТТГ в неправильной единице (`мкМЕ/мл` вместо `мМЕ/л`).
2. Открывает список замеров, находит нужный (фильтр по дате).
3. Заходит в карточку замера, нажимает «Редактировать».
4. Исправляет единицу и значение.
5. Сохраняет. Возвращается на карточку — данные обновлены, флаг отклонения пересчитан.
6. Открывает график ТТГ — точка сместилась в правильное положение.

**Ожидаемый результат**: изменения сохранены, `updatedAt` обновлён, графики пересчитаны.

### Сценарий 5. Регистрация второго члена семьи

1. Администратор (он же первый пользователь) отправляет мужу ссылку инсталляции.
2. Муж регистрируется со своими данными (e-mail отличается).
3. Начинает вводить свои замеры.
4. Оба пользователя видят **только свои** замеры, показатели, вложения. Переключения между аккаунтами нет — каждый в своей сессии.

**Ожидаемый результат**: полная изоляция данных. Этот сценарий проверяется автоматическим тестом.

### Сценарий 6. Восстановление после катастрофы

1. Администратор случайно удалил volume с БД.
2. Берёт последний бэкап (созданный кроном ночью).
3. Запускает `docker compose exec api pnpm backup:restore ./backups/backup-2026-04-24-0300.tar.gz --yes`.
4. Контейнер api перезапускается, миграции применяются поверх восстановленной БД.
5. Пользователи заходят — видят все свои данные на состояние последнего бэкапа.

**Ожидаемый результат**: потеря данных — максимум 1 сутки (интервал бэкапа).
